# AWS S3: 수천만 대 디스크로 어떻게 스케일하는가

## 도입 배경

S3는 단순한 파일 저장소가 아니다. 아래 수치를 보면 그 규모가 얼마나 압도적인지 알 수 있다.

- **400조 개** 이상의 객체 저장
- **초당 1.5억 건** 요청 처리
- **초당 1PB 이상** 피크 트래픽
- **수천만 대** HDD 운영

문제는 이 스케일을 HDD로 달성해야 한다는 점이다. HDD는 지난 수십 년간 용량 대비 가격이 61억 배 저렴해졌지만, **무작위 접근 성능은 거의 개선되지 않았다** (약 32MB/s 수준). 물리적 기계 운동(헤드 이동, 디스크 회전)이 근본적인 병목이다.

> 핵심 질문: "느린 개별 디스크들을 어떻게 묶어서 세계에서 가장 빠른 오브젝트 스토리지를 만드는가?"

---

## 요약

### 1. HDD의 물리적 한계

단일 HDD의 무작위 I/O 지연 구성:

| 요소 | 소요 시간 |
|------|-----------|
| 탐색(Seek) 지연 | 약 8~9ms |
| 회전(Rotational) 지연 | 약 4ms |
| 데이터 전송 (0.5MB 기준) | 약 2.5ms |
| **합계** | **약 15ms** |

SSD 대비 수십 배 느리다. 하지만 **비용 효율**과 **대용량** 측면에서 HDD는 여전히 대규모 오브젝트 스토리지의 유일한 선택지다.

---

### 2. 삭제 코딩(Erasure Coding)

S3의 핵심 내구성 메커니즘이다. 3배 복제(Replication) 대신 사용한다.

**방식:** 데이터를 **5개 데이터 샤드 + 4개 패리티 샤드** (총 9조각)로 분산 저장. 9개 중 5개만 있으면 원본 복원 가능.

**트레이드오프:**

| | 3배 복제 | 삭제 코딩 (5+4) |
|--|---------|----------------|
| 저장소 오버헤드 | 3배 | 1.8배 |
| 허용 장애 수 | 2개 | 4개 |
| 읽기 부하 분산 | 3개 소스 | 5개 소스 |
| 복구 연산 비용 | 낮음 | 높음 |

저장 비용을 40% 절감하면서 더 높은 내구성을 달성한다. 단, 복구 시 연산 오버헤드가 발생한다.

---

### 3. 병렬화 전략

**세 계층의 병렬화:**

```
클라이언트
  └── 멀티파트 업로드 / 범위 GET (청크 병렬 처리)
        └── 다중 프론트엔드 서버
              └── 여러 스토리지 백엔드에 샤드 분산
```

핵심 사고 방식:
> "1GB/s를 단일 서버 1대에서 처리하는 것보다, 100개 서버에서 각 10MB/s씩 처리하는 게 훨씬 쉽다."

단일 디스크의 느린 속도는 **충분히 많은 디스크를 병렬로 묶으면** 극복 가능하다.

---

### 4. 핫스팟 회피

부하가 특정 노드에 쏠리는 핫스팟은 대규모 시스템의 고질적 문제다. S3는 세 가지로 대응한다.

**① Power of Two 랜덤 선택**

완전 무작위로 노드를 선택하면 확률적으로 과부하 노드에 요청이 몰린다. 대신, **무작위로 두 노드를 고르고 부하가 낮은 쪽을 선택**하면 로드 밸런싱 품질이 극적으로 개선된다.

**② 데이터 재조정(Rebalancing)**

- 신규 데이터는 접근 빈도가 높고, 시간이 지나면서 점차 냉각됨
- 새 디스크 랙 추가 시 자동으로 데이터 재배치
- 지속적 리밸런싱으로 균형 유지

**③ 규모의 안정화 효과**

시스템이 커질수록 오히려 더 예측 가능해진다. 수백만 명의 독립적인 사용자 요청이 동시에 버스트할 가능성은 낮기 때문에, 집계 트래픽은 평탄화(decorrelation)된다.

---

### 5. 스토리지 백엔드: ShardStore

S3 내부 스토리지 엔진으로, **LSM 트리(Log-Structured Merge-Tree)** 기반이다.

- **쓰기:** 순차 접근 → HDD 성능 최적화
- **읽기:** 무작위 접근이지만 병렬화로 커버

LSM을 선택한 이유: HDD는 순차 I/O가 무작위 I/O보다 수십 배 빠르다. 쓰기를 항상 순차적으로 처리함으로써 HDD의 약점을 우회한다.

---

### 6. 추가 레이턴시 최적화

**헤지 요청(Hedged Request):**
p95 지연을 초과하는 느린 요청이 발생하면, 다른 호스트로 동일 요청을 추측적(speculative)으로 보내고 먼저 응답이 오는 것을 사용한다. 느린 노드의 영향을 차단.

**DNS 레벨 셔플 샤딩:**
클라이언트별로 다른 서버 집합을 바라보게 해 자연스러운 부하 분산을 유도한다.

**실측 지연 (0.5MB 객체 기준):**
- p50: 약 26ms
- p99: 약 140ms

## 핵심 패턴

S3에서 추출할 수 있는 범용 설계 패턴들이다.

### 패턴 1: 복제 대신 삭제 코딩
- **언제:** 대용량 데이터를 저비용으로 저장해야 할 때
- **원리:** 수학적 패리티로 3배 복제 수준의 내구성을 1.8배 오버헤드로 달성
- **트레이드오프:** 복구 연산 비용 증가, 읽기 지연 소폭 증가
- **적용 사례:** HDFS, Ceph, Azure Blob Storage

### 패턴 2: 병렬화로 단일 노드 한계 극복
- **언제:** 단일 노드 성능이 요구 사항을 충족하지 못할 때
- **원리:** 문제를 수평으로 분할해 충분한 수의 노드에 분산
- **트레이드오프:** 조율(coordination) 복잡도 증가
- **적용 사례:** Kafka 파티션, 데이터베이스 샤딩, MapReduce

### 패턴 3: Power of Two 랜덤 선택
- **언제:** 여러 노드 중 하나를 선택해야 할 때 (로드 밸런싱, 노드 배치)
- **원리:** 두 후보를 무작위 선택 후 더 나은 쪽을 고르면 O(log log n) 수준의 최대 부하로 수렴
- **트레이드오프:** 최적이 아닌 near-optimal이지만 연산이 극히 단순
- **적용 사례:** Nginx upstream, Cassandra vnodes, Envoy

### 패턴 4: 헤지 요청 (Speculative Execution)
- **언제:** tail latency(p99, p99.9)를 줄여야 할 때
- **원리:** 느린 요청을 기다리지 않고 다른 서버에 중복 요청, 먼저 온 응답 사용
- **트레이드오프:** 리소스 낭비 (중복 요청), 멱등성 필요
- **적용 사례:** Google BigTable, Hadoop, DynamoDB read repair

### 패턴 5: LSM 트리로 쓰기 순차화
- **언제:** 쓰기 집약적 워크로드에서 HDD(또는 느린 저장 매체)를 사용할 때
- **원리:** 무작위 쓰기를 메모리에 버퍼링 후 순차적 플러시로 변환
- **트레이드오프:** 읽기 증폭(Read Amplification), 컴팩션 오버헤드
- **적용 사례:** RocksDB, Cassandra, LevelDB
